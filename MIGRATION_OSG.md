# MIGRATION_OSG

Технический паспорт legacy Excel-контура ОСГ и baseline для будущего
сравнения Excel → JSON/API 1С.

Документ фиксирует текущее поведение. Спорные бизнес-правила не изменяются
до отдельного решения.

## CURRENT EXCEL CONTRACT

### Источник

- Папка: `data/raw`.
- Загрузчик: `src.loader.load_latest_file()`.
- Формат: `.xlsx`.
- Выбирается файл с максимальным временем изменения.
- Временные файлы открытого Excel с префиксом `~$` исключаются.
- Первая строка данных определяется через `header=7`.
- Для regression baseline используется `data/raw/osg_2026_05_22.xlsx`.
- Лист эталонного файла: `TDSheet`.

Эталонный файл исключён из Git правилом `data/raw/`. Regression test зависит
от его наличия в локальной рабочей папке.

### Входные колонки

| Excel | Рабочая колонка |
|---|---|
| `Склад` | `Склад` |
| `Номенклатурная группа` | `Категория_исходная` |
| `Номенклатура` | `SKU_исходный`, затем нормализованный `SKU` |
| `Срок годности` | `Срок годности_исходная`, затем дата `Срок годности` |
| `Характеристика номенклатуры` | `Контейнер` |
| первое `В ед. хранения` | `Остаток` |
| второе `В ед. хранения` (`.1`) | `Зарезервировано` |
| третье `В ед. хранения` (`.2`) | `Свободный остаток` |

Пустая техническая колонка `Unnamed: 0` не используется.

### Pipeline

1. Очистка пробелов в названиях колонок.
2. Переименование колонок 1С.
3. Сохранение исходного названия товара в `SKU_исходный`.
4. Формирование аналитического `SKU`.
5. Приведение характеристики/контейнера к тексту.
6. Удаление пустых строк, строк без SKU и строки `ИТОГ`.
7. Разбор срока годности формата `ДД.ММ.ГГГГ 0:00:00`.
8. Определение веса из названия SKU.
9. Определение аналитической категории.
10. Определение полного срока жизни.
11. Расчёт `days_left` и `ОСГ %`.
12. Validation выполняется по полному набору строк.
13. Данные делятся на основную аналитику `Остаток > 100` и отдельную таблицу
    малых остатков `Остаток <= 100`.
14. Для основной аналитики рассчитываются риск, KPI и таблицы.

Нормализация SKU выполняется до веса, категории, срока жизни, фильтров и всех
`groupby`.

## DATE SEMANTICS

### Current view

```text
calculation_date = текущая календарная дата
```

Обычный вызов `calculate_osg(df)` использует `datetime.today()`, после чего
время нормализуется до начала текущего календарного дня. Утренний и вечерний
расчёт одной даты дают одинаковый результат.

### Historical view

```text
calculation_date = выбранная stock_date
```

Для исторического снимка ОСГ должен показывать состояние на дату снимка, а не
пересчитываться на сегодняшний день.

### Legacy Excel regression

```text
calculation_date = 22.05.2026
```

22.05.2026 — фиксированная техническая regression date. Основания:

- имя `osg_2026_05_22.xlsx`;
- Windows `CreationTime`: 22.05.2026 16:40:52 MSK;
- Windows `LastWriteTime`: 22.05.2026 16:41:11 MSK;
- XLSX `created/modified`: 22.05.2026 13:41:11 UTC.

Эта дата не считается доказанным `stock_date`: отдельного надёжного поля даты
снимка в legacy Excel нет.

Дата 31.05.2026 внутри отчёта — техническая конечная дата параметра
формирования отчёта 1С. Она:

- не является `stock_date`;
- не является фактической датой выгрузки;
- не используется как `calculation_date`;
- не участвует в regression baseline.

Будущий API должен отдавать реальную дату состояния остатков в `stock_date`.

## SKU NORMALIZATION

### Разделение исходного и аналитического названия

- `SKU_исходный` — неизменённое название из 1С для трассировки.
- `SKU` — нормализованное аналитическое название BIBICALL.

Во всех текущих фильтрах, расчётах, группировках и пользовательских таблицах
используется `SKU`.

### Подтверждённые правила

1. Удалить пробелы по краям.
2. Удалить только ведущую техническую `*` и пробелы после неё.
3. Заменить последовательность пробельных символов одним пробелом.
4. Если название заканчивается обозначением `г` без точки, привести его к
   `г.`.
5. Не менять регистр, цифры, формулу, вес, размер упаковки и слова.
6. Не применять fuzzy matching.

Нормализация названия не удаляет строки и не объединяет партии. На детальном
уровне сохраняются контейнер, срок годности и все три количества. Объединение
нормализованного SKU происходит только в существующих сводных `groupby`.

### Фактические технические варианты 20.08.2026

| Исходное название | Аналитический SKU | Причина |
|---|---|---|
| `* НЭННИ .3 с пребиотиками 800 г.` | `НЭННИ .3 с пребиотиками 800 г.` | ведущая техническая `*` |
| `* НЭННИ 1 400 г.` | `НЭННИ 1 400 г.` | ведущая техническая `*` |
| `* НЭННИ 1 800 г.` | `НЭННИ 1 800 г.` | ведущая техническая `*` |
| `* НЭННИ 2 800 г` | `НЭННИ 2 800 г.` | `*` и точка после `г` |
| `* НЭННИ  4 400 гр.` | `НЭННИ 4 400 гр.` | `*` и повторный пробел |
| ` НЭННИ  Классика 400 гр.` | `НЭННИ Классика 400 гр.` | крайний и повторный пробел |

### Причина прежнего разделения SKU

В модуле ОСГ отсутствовала функция, записывающая нормализованное название в
колонку `SKU`. `src.osg.calculator.normalize_text()` использовалась только
внутри определения срока жизни и не изменяла данные для Streamlit. Поэтому
исходные варианты со `*` доходили до фильтров и `groupby` как отдельные SKU.

## BUSINESS RULES

### Вес

- Первое число перед `г` извлекается из SKU.
- Десятичная запятая заменяется точкой.
- Флоупак печенье Грушевое: 37.5 г.
- Шоубокс печенье Грушевое: 750 г (`20 × 37.5`).

### Категории

- Флоупак печенье → `ФЛОУПАК_ПЕЧЕНЬЕ`.
- Шоубокс печенье → `ШОУБОКС_ПЕЧЕНЬЕ`.
- Мясные консервы → `ПЮРЕ МЯСНЫЕ консервы`.
- Рыбные консервы → `ПЮРЕ РЫБНЫЕ консервы`.
- Творожное пюре → `ПЮРЕ ТВОРОЖНОЕ`.
- НЭННИ делится на `НЭННИ 400` и `НЭННИ 800` по весу.
- Остальные категории сохраняются.

### Формула ОСГ

```text
days_left = expiry_date - calculation_date
ОСГ % = days_left / total_days × 100
```

Значение не ограничивается диапазоном 0–100.

### Уровни риска

| ОСГ | Уровень |
|---|---|
| `>= 75` | Свежий |
| `70–<75` | Хороший |
| `66–<70` | Норма |
| `60–<66` | Внимание |
| `50–<60` | Пограничный |
| `40–<50` | Горящий |
| `20–<40` | Критично |
| `<20` | Списание |

### Фильтры и показатели

- Основная аналитика: `Остаток > 100`.
- Отдельный контроль малых остатков: `Остаток <= 100`.
- Validation выполняется до разделения на эти представления.
- Срочно продать: после агрегации `Категория + Analytical SKU +
  Срок годности` применяются `ОСГ < 60` и `Свободный остаток > 0`.
  Технический порог 80 шт. не используется. Доля резерва рассчитывается как
  `Зарезервировано / Остаток * 100`; при нулевом остатке результат остаётся пустым.
- Сводный SKU: суммы количеств и минимальный ОСГ среди партий.

Блок «Где заморожены деньги» временно исключён из пользовательского
интерфейса, поскольку бизнес-логика показателя ещё не определена и требует
отдельного проектирования. Старый inline-расчёт удалён из `page.py`; отдельных
переиспользуемых функций у него не было.

## QUALITY DIAGNOSTICS

Диагностика подключена к нижнему техническому блоку Streamlit и не изменяет
расчёты.

Проверяются:

- пустые SKU;
- пустые сроки годности;
- пустые категории и значение `Не определено`;
- нечисловые и отрицательные количества;
- `Остаток - Зарезервировано = Свободный остаток`;
- `null` отдельно по каждому количеству;
- дубли предполагаемого ключа;
- fallback срока жизни;
- остаточные технические признаки SKU;
- невозможность получить аналитический SKU из непустого исходного имени.

## KNOWN AMBIGUITIES / REQUIRES BUSINESS DECISION

1. Legacy Excel не содержит надёжного `stock_date`.
2. Не подтверждено, является ли `Характеристика номенклатуры` всегда
   контейнером.
3. Не решено, означает ли `null` в резерве/free ноль или неизвестное значение.
4. Fallback 730 остаётся защитным правилом для будущих нераспознанных товаров.
5. После нормализации выгрузки 20.08.2026 обнаружены 10 строк с одинаковым
    предполагаемым ключом `Склад + SKU + Контейнер + Срок годности`. Строки не
    удаляются и не объединяются на детальном уровне.

Автоматически неоднозначные похожие названия не объединялись. Фактические
объединения 20.08.2026 объясняются только подтверждёнными техническими
правилами `*`, пробелов и точки после `г`.

## FUTURE API CONTRACT

Ожидаемый endpoint: `GET /api/v1/stocks`.

### Предварительно сопоставленные поля

| API | Текущий Excel/аналитика |
|---|---|
| `stock_date` | В legacy Excel надёжного аналога нет |
| `warehouse_name` | `Склад` |
| `product_name` | `SKU_исходный`; затем нормализация в `SKU` |
| `product_group` | `Категория_исходная` |
| `characteristic_name` | текущий `Контейнер`, требует подтверждения |
| `expiry_date` | `Срок годности` |
| `shelf_life_days` | текущий `total_days`, сейчас определяется Python |
| `quantity_total` | `Остаток` |
| `quantity_reserved` | `Зарезервировано` |
| `quantity_free` | `Свободный остаток` |

### Требуют подтверждения по реальному JSON

- стабильность `product_id` и `product_code`;
- структура характеристики и серии/партии;
- бизнес-ключ строки снимка;
- семантика `null`;
- единицы измерения;
- источник полного срока жизни;
- пагинация и metadata;
- реальная семантика `stock_date`.

Будущий API должен отдавать исходные идентификаторы и названия 1С.
Нормализация аналитического SKU остаётся ответственностью BIBICALL и не
переносится автоматически в 1С.

Конкретный API-клиент, JSON parser и окончательная API-схема до получения
реального JSON не создаются.
