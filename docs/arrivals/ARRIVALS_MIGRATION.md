# ARRIVALS: миграция Excel → версионируемые источники и API 1С

Документ описывает безопасный переход без изменения подтверждённых расчётов и
UI до достижения parity. Окончательный контракт JSON и письмо программисту 1С
создаются на следующем этапе.

## 1. Текущий pipeline

```text
Excel history
Excel actual 1С
Excel Daniel (последний по mtime)
        ↓
pandas loaders / transformers
        ↓
единый arrivals DataFrame
        ↓
fact-over-plan и reconciliation
        ↓
Streamlit / Excel export
```

Текущие компоненты:

- `src/arrivals/loader.py` выбирает последний Excel по filesystem `mtime`;
- `src/arrivals/transformer.py` приводит историю, факт и Daniel к общей
  плоской структуре;
- `src/arrivals/calculator.py` выполняет reconciliation контейнеров и
  замещение плана фактом;
- `src/arrivals/page.py` собирает процесс обработки и UI;
- `src/arrivals/exporter.py` формирует финансовую Excel-выгрузку.

`data/arrivals/plan/arrivals_plan_2026_2027.xlsx` объявлен в конфигурации, но не
используется текущим процессом обработки. Включать его без отдельного решения нельзя.

## 2. Целевой pipeline

```text
Daniel raw snapshot archive
        ↓
Daniel normalized versioned snapshots
        ↓
DanielSnapshot + DanielSourceRecord
        ↓
представление последнего подтверждённого плана

1C API raw movements
        ↓
MovementSourceRecord
        ↓
классификация по подтверждённым правилам документов/движений
        ├─ ReceiptSourceRecord
        ├─ CostMovementRecord
        └─ Return/Correction records
        ↓
normalized actual arrivals

последний подтверждённый план + валидные физические приходы
        ↓
container reconciliation / fact-over-plan
        ↓
ArrivalAnalyticalRecord
        ↓
Streamlit / exports / future OSG-FEFO
```

## 3. Что сохранить

При миграции сохраняются без изменения до отдельного бизнес-решения:

- Daniel как источник оперативного плана;
- последний подтверждённый snapshot без суммирования истории;
- исходный grain Daniel и допустимые повторы `container + SKU`;
- ETD +70 дней для смесей и +14 дней для каш;
- отдельные `expected_arrival_date` и `arrival_week_start`;
- строки Daniel без контейнера и статус `⚪ Контейнер не назначен`;
- замещение плана фактом на уровне контейнера для валидного физического факта;
- отсутствие частичной reconciliation по SKU;
- текущие восемь статусов reconciliation;
- 1С как источник истины по фактическому составу и количеству;
- текущие KPI, финансовая таблица и Excel-выгрузка до принятия новой модели;
- регрессионные итоги и тесты как контроль parity.

## 4. Что добавить

- версионируемый архив raw и normalized файлов Daniel;
- `snapshot_id`, дата/версия/статус snapshot и версия схемы;
- точные даты FILL, ETD, ожидаемого и фактического прихода;
- raw-слой движений 1С со стабильными ID;
- классификация до нормализации quantity;
- отдельные сущности физических приходов и затрат;
- проверка качества ссылки на контейнер/поставку;
- поля серии, производства и срока годности;
- статусы posted/deleted/reposted и `last_modified_at`;
- возвраты/корректировки как отдельные типы движений;
- архив raw payload, метаданные аудита и идемпотентная загрузка.

## 5. Что заменять только после достижения parity

После параллельного сравнения Excel и API можно заменить:

- выбор Daniel/actual по filesystem `mtime`;
- смещения заголовков и названия колонок, специфичные для Excel;
- разбор отображаемой строки регистратора вместо стабильных ID;
- использование `По неделям` вместо точной даты;
- общую плоскую исходную модель;
- ранний `fillna(0)`;
- потерю FILL/Booking/Carrier/SHIP;
- округление ожидаемой даты прихода до недели без сохранения точной даты.

Legacy-загрузчики Excel не удаляются до подтверждённого parity и периода
стабилизации.

## 6. Миграция snapshots Daniel

Целевая структура:

```text
data/arrivals/daniel/raw/
    daniel_original_YYYY-MM-DD_vN.xlsx

data/arrivals/daniel/normalized/
    daniel_shipments_plan_YYYY-MM-DD_vN.xlsx
```

Порядок:

1. Архивировать оригинал без редактирования.
2. Создать нормализованный файл с устойчивым набором колонок.
3. Зарегистрировать дату/версию snapshot и связь raw ↔ normalized.
4. Провести проверку схемы и качества данных.
5. Явно подтвердить snapshot.
6. Перестроить текущее представление плана из последнего подтверждённого snapshot.
7. Никогда не суммировать snapshots.

Исторические версии используются только для анализа изменений. Номер строки годится
для трассировки внутри версии, но не для сопоставления между snapshots.

## 7. Миграция движений 1С

1. Получить реальный обезличенный ответ API без предположений о схеме.
2. Согласовать grain, стабильные ID, даты, допустимость null и типы документов.
3. Сохранить raw-ответ и версию схемы.
4. Создать `MovementSourceRecord` без потери null.
5. Классифицировать движения по подтверждённым правилам.
6. Создать физические приходы и финансовые движения раздельно.
7. Сохранять неизвестные/новые типы документов в карантине/диагностике, а не
   молча включать в приходы.
8. Реализовать идемпотентный upsert по стабильным ID и потоку изменений.
9. Только затем формировать нормализованные фактические приходы.

`Поступление товаров и услуг` остаётся предварительным кандидатом физического прихода, а не
навсегда зашитым исчерпывающим списком.

## 8. Проверки качества данных

До аналитического слоя проверяются:

- обязательные ID и даты источника;
- классификация документа/движения;
- quantity со значением null согласно типу движения;
- единица и числовой тип quantity;
- статусы posted/deleted/cancelled;
- ссылка на контейнер/поставку физического прихода;
- отсутствие `null`, пустого, `0` и `"0"` у валидного физического факта;
- уникальность исходной строки по стабильным ID;
- полнота страниц API и контроль `count`;
- согласованность серии и срока годности, когда поля доступны.

Ошибочный физический факт сохраняется и диагностируется. Невалидная ссылка на
контейнер/поставку не закрывает план Daniel; значение не угадывается.

## 9. Стратегия проверки parity

Excel и API сравниваются на одном согласованном периоде:

1. число raw-движений по типу документа;
2. число строк физического прихода;
3. итоги quantity по документу, контейнеру, SKU и периоду;
4. точные даты и расчёт начала недели;
5. Mapping исходного SKU в аналитический SKU;
6. статусы reconciliation по контейнерам;
7. результат замещения плана фактом;
8. текущие KPI и выгрузки;
9. отдельные итоги cost movements без включения в quantity приходов;
10. ошибки качества данных и неизвестные типы документов.

Расхождения документируются и принимаются пользователем до переключения UI.

## 10. Последовательность внедрения

1. Проверить бизнес-правила и модель данных C2B.
2. Подготовить вопросы и предварительную спецификацию API для 1С.
3. Получить пример JSON и ответы по семантике.
4. Зафиксировать версионируемый contract fixture.
5. Реализовать адаптеры источников и валидацию отдельно от бизнес-расчётов.
6. Выполнить теневую загрузку API рядом с Excel.
7. Достичь parity строк, агрегатов и reconciliation.
8. Переключить сервисный слой на API с контролируемым fallback в период
   стабилизации.
9. Отключать загрузку Excel только отдельным решением.
10. После стабилизации подключать серию и срок годности к OSG/FEFO.

## 11. Откат и наблюдаемость

- Каждый запуск загрузки получает ID, timestamp источника и версию схемы.
- Raw payload и выбранный snapshot Daniel доступны для аудита.
- Метрики показывают строки по типу документа, итоги quantity, отклонённые
  записи и ошибки качества данных.
- Неизвестный тип документа не меняет текущие KPI автоматически.
- Переключение источника выполняется через feature/config flag, чтобы можно было
  вернуться к проверенному адаптеру Excel без изменения бизнес-расчётов.

## 12. Текущий технический долг

- Последний Daniel snapshot определяется по `mtime`.
- Точная `expected_arrival_date` теряется.
- Точная фактическая `Дата` не используется.
- ГТД может пройти как `Факт 1С` с quantity `0`.
- `fillna(0)` выполняется до семантической классификации.
- FILL, Booking, Carrier и SHIP теряются.
- Исходные и аналитические поля смешаны.
- Стабильные ID 1С отсутствуют.
- Срок годности/серия отсутствуют.
- `arrivals_plan_2026_2027.xlsx` объявлен, но не используется.

Эти пункты не исправляются на этапе документации C2B.

## 13. ОТКРЫТЫЕ БИЗНЕС-ВОПРОСЫ

1. Полный перечень документов физического прихода.
2. Официальная бизнес-дата фактического прихода.
3. Правила включения возвратов/корректировок в будущие KPI.
4. Требуемая управленческая модель landed cost.
5. Семантика общей ссылки на контейнер/поставку.
6. Назначение legacy-файла `arrivals_plan_2026_2027.xlsx`.

## 14. ОТКРЫТЫЕ ТЕХНИЧЕСКИЕ ВОПРОСЫ И ВОПРОСЫ К 1С

- Регистр, grain и стабильные ID физических/финансовых движений.
- Дата и время документа, проведения, движения и поступления на склад.
- Хранение ссылки на контейнер/поставку у импортных и российских поставщиков.
- Серия, дата производства, срок годности и их grain.
- Связь ГТД, поступления и дополнительных расходов.
- UUID строк, изменения, удаления, перепроведение и инкрементальный API.
- Пагинация, контроль полноты, повторы/идемпотентность и версионирование схемы.

Окончательная схема API не фиксируется до получения этих ответов и реального
примера JSON.
