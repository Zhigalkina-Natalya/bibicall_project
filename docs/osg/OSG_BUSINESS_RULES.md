# ОСГ: бизнес-правила

Главный источник истины по действующей бизнес-логике ОСГ. Кодовые ссылки:
`src/osg/calculator.py`, `src/osg/rules.py`, `src/osg/transformer.py`.

## 1. Семантика дат

### Актуальное состояние

```text
calculation_date = текущая календарная дата
```

`calculate_osg(df)` использует `datetime.today()`, затем нормализует значение до
начала календарного дня. Время запуска внутри одного дня не влияет на результат.

### Историческое состояние

```text
calculation_date = stock_date выбранного исторического снимка
```

Исторический снимок нельзя пересчитывать на сегодняшнюю дату. Функция уже
поддерживает явный параметр `calculation_date`; выбор исторического снимка в UI
ещё не реализован.

### Legacy regression

- `22.05.2026` — техническая фиксированная дата теста файла
  `data/raw/osg_2026_05_22.xlsx`.
- Она выбрана по имени и metadata файла, но не является доказанным `stock_date`.
- `31.05.2026` внутри отчёта — техническая конечная дата периода формирования
  отчёта 1С. Это **не** `stock_date`, **не** `calculation_date` и **не** дата
  фактического состояния остатков.
- Будущий API обязан передавать реальный `stock_date`.

## 2. Формула ОСГ

```text
days_left = expiry_date - calculation_date
OSG % = days_left / shelf_life_days × 100
```

В текущем DataFrame `shelf_life_days` называется `total_days`. Значение ОСГ не
ограничивается диапазоном 0–100: просрочка даёт отрицательное значение, а срок
дальше полного периода может дать значение выше 100.

## 3. Уровни ОСГ

| ОСГ % | Уровень |
|---|---|
| `>=75` | Свежий |
| `70–<75` | Хороший |
| `66–<70` | Норма |
| `60–<66` | Внимание |
| `50–<60` | Пограничный |
| `40–<50` | Горящий |
| `20–<40` | Критично |
| `<20` | Списание |

Название `ОК` устарело. Для диапазона `70–<75` используется только `Хороший`.
Границы закреплены тестами в `tests/test_osg_rules.py`.

## 4. Legacy shelf life

### Категории

| Нормализованная категория/правило | Дней |
|---|---:|
| ПЕЧЕНЬЕ | 365 |
| БИБИКАША | 456 |
| ПЮРЕ МОЛОЧНОЕ | 547 |
| ПЮРЕ ТВОРОЖНОЕ | 730 |
| МЯСНЫЕ КОНСЕРВЫ | 730 |
| РЫБНЫЕ КОНСЕРВЫ | 730 |
| АМАЛТЕЯ | 1080 |

Source-варианты `ТВОРОЖНОЕ ПЮРЕ` и `ПЮРЕ ТВОРОЖНОЕ` в pipeline приводятся к
единой аналитической категории `ПЮРЕ ТВОРОЖНОЕ` и получают 730 дней. Отдельного
правила 547 для творожного пюре нет.

### НЭННИ

- Классика 400/800, `.3` 400/800, формулы 1, 2 и 3 в весах 400/800 — 912 дней.
- НЭННИ 4 400/800 — 730 дней.
- `НЭННИ (ЗК) 3 800` нормализуется в `НЭННИ 3 800 г.` и получает 912 дней.

### Fallback

`Fallback 730` — защитное legacy-поведение для неизвестного SKU/категории, а не
универсальный подтверждённый срок. Подтверждённые правила со значением 730 не
помечаются как fallback.

**OPEN DECISION — API shelf life priority.** После получения JSON нужно решить,
является ли `shelf_life_days` из 1С единственным источником или допускается
проверочный Python fallback. До решения legacy fallback не удаляется.

## 5. Source SKU и Analytical SKU

- **Source SKU** (`SKU_исходный`) — исходное техническое наименование 1С для
  traceability.
- **Analytical SKU** (`SKU`) — нормализованное бизнес-наименование для аналитики.

Подтверждённая нормализация:

1. пробелы по краям;
2. ведущая техническая `*`;
3. повторные пробельные символы;
4. точка после завершающего обозначения `г`;
5. mapping `НЭННИ (ЗК) 3 800 гр.` → `НЭННИ 3 800 г.`.

Fuzzy matching не применяется. Нормализация не меняет смысловые цифры, формулу,
вес или размер упаковки.

Детальные строки сохраняются раздельно по складу, характеристике/контейнеру и
сроку. В сводках технические варианты одного товара агрегируются по Analytical
SKU. Строки с разными бизнес-ключами нельзя объединять молча.

## 6. Вес и категория

- Вес извлекается как первое число перед `г`; запятая преобразуется в точку.
- Флоупак печенье Грушевое — 37,5 г.
- Шоубокс печенье Грушевое — 750 г (`20 × 37,5`).
- Флоупак/Шоубокс получают отдельные аналитические категории.
- Мясные, рыбные и творожные пюре получают нормализованные категории.
- НЭННИ делится на `НЭННИ 400` и `НЭННИ 800` по извлечённому весу.

## 7. Основная аналитика и малые остатки

Validation полного набора выполняется **до** разделения.

```text
Основная аналитика: Остаток > 100
Малые остатки:      Остаток <= 100
```

Границы: 100 → малые остатки; 101 → основная аналитика. Малые остатки не
удаляются и показываются отдельно для проверки наличия, брака/непригодности,
маркетинга, благотворительности и других операционных решений. Автоматическое
назначение таким остаткам не присваивается.

## 8. «Что нужно срочно продать»

Источник — основная аналитика. Порядок обязателен:

1. агрегировать `Категория + Analytical SKU + Срок годности`;
2. суммы: Остаток, Зарезервировано, Свободный остаток;
3. ОСГ %: минимум;
4. после агрегации применить `ОСГ % < 60` и `Свободный остаток > 0`.

Старый порог `Свободный остаток >= 80` не является актуальным правилом.

```text
Доля резерва, % = Зарезервировано / Остаток × 100
```

При Остатке 0 результат остаётся пустым, деление на ноль не выполняется.

## 9. Data quality

- `run_all_checks()` и `run_quality_diagnostics()` получают полный набор до
  разделения и UI-фильтров.
- Expired goods диагностируются по отрицательному ОСГ.
- Проверяются обязательные поля, даты, вес, shelf life, null, числовые типы,
  отрицательные количества и баланс `total - reserved = free`.
- Duplicate candidates выявляются по предполагаемому ключу
  `Склад + SKU + Контейнер + Срок годности`, но не удаляются автоматически.
- Совпадение Source SKU после normalization само по себе не является ошибкой;
  исходные строки и `SKU_исходный` сохраняются.
- Суммы двух представлений должны сходиться с полным набором.

**OPEN DECISION — null semantics.** Не определено, означает ли `null` в резерве
или свободном остатке ноль либо неизвестное значение.

**OPEN DECISION — duplicate policy.** Предполагаемый ключ ещё не утверждён;
автоматическая дедупликация запрещена.

Технический статус нерассчитанного ОСГ имеет единое внутреннее значение
`Ошибка`. Эмодзи не является частью ключа данных или значения фильтра.

## 11. Presentation rules

Согласованный порядок страницы:

1. заголовок ОСГ;
2. KPI;
3. остатки по категориям;
4. что нужно срочно продать;
5. SKU по ОСГ с риском;
6. сводная таблица по категориям и SKU;
7. малые остатки `<=100`;
8. полная таблица со складами;
9. калькулятор ОСГ;
10. ошибки, expired goods и quality diagnostics в нижней технической части.

Дополнительные правила:

- пользовательские таблицы показываются без pandas index;
- risk/OSG formatting единообразны;
- risk и summary tables расположены вертикально;
- small stock: SKU → склад → expiry по возрастанию;
- full stock: категория → SKU → склад → expiry по возрастанию;
- Excel-export не содержит index и сохраняет смысловую цветовую индикацию.

Блок «Где заморожены деньги» неактивен: бизнес-логика не подтверждена, UI и
старый inline-расчёт удалены.
